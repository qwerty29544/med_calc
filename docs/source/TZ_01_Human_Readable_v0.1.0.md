# Техническое задание на разработку системы поддержки принятия врачебных решений по антибактериальной терапии

**Версия:** 0.1.0  
**Статус:** рабочая спецификация текущего этапа  
**Аудитория:** медицинская команда, руководители проекта, аналитики, разработчики  
**Назначение документа:** зафиксировать понятным человеческим языком, какую систему мы разрабатываем сейчас, что должна реализовать техническая команда и какие клинические данные должны быть предоставлены и валидированы медицинской командой.

---

## 1. Назначение системы

Необходимо разработать автономное веб-приложение поддержки врачебных решений для выбора антибактериальной терапии у взрослых амбулаторных пациентов. Система не ставит диагноз и не заменяет клиническое решение врача. Она выполняет заранее утвержденные медицинские правила, показывает полученный результат и объясняет, какие данные пациента и какие правила привели к этому результату.

Версия 0.1.0 должна реализовать шесть нозологий:

1. хронический бронхит;
2. острый бронхит;
3. пневмония;
4. обострение ХОБЛ;
5. фарингит/тонзиллит;
6. синусит.

Медицинская логика этих шести нозологий зафиксирована как **ruleset 0.1.0** и уже переведена из презентации в машинное представление. Логические расхождения исходной презентации, которые ранее были отдельно согласованы, нормализуются техническими правилами версии 0.1.0 и остаются видимыми в аудите.

## 2. Что представляет собой продукт

Продукт состоит не из одного «калькулятора», а из нескольких последовательных этапов обработки клинического случая.

```text
Данные клинического случая
        ↓
Клиническое дерево нозологии
        ↓
Предварительная схема лечения
        ↓
Разрешение схемы в конкретные препараты
        ↓
Проверка противопоказаний
        ↓
Проверка лекарственных взаимодействий
        ↓
Коррекция дозы, если имеются правила и данные
        ↓
Формирование итоговой рекомендации
        ↓
Объяснение решения + сохранение результата + обратная связь врача
```

Каждый этап должен быть технически отделен от остальных. Это необходимо, чтобы медицинская команда могла обновлять противопоказания, взаимодействия и дозовые правила независимо от клинических деревьев нозологий.

## 3. Основные принципы версии 0.1.0

### 3.1. Детерминированная логика

Система не использует генеративный ИИ для выбора лечения. Для одинакового набора входных данных и одинаковых версий правил система обязана выдавать одинаковый результат.

### 3.2. Объяснимость

Для каждого расчета система должна сохранять и уметь показать последовательность решения: какие признаки использованы, какие баллы рассчитаны, какая ветвь выбрана, какие препараты были кандидатами, какие были исключены и по какой причине.

### 3.3. Версионирование

Любое медицинское решение связано с конкретными версиями клинических правил, справочника препаратов, правил противопоказаний, взаимодействий и дозирования. Опубликованная версия медицинского контента не изменяется задним числом.

### 3.4. Отделение медицинского контента от программного кода

Разработчик не должен вручную переписывать исходный код приложения при каждом изменении клинической рекомендации. Медицинские правила должны поступать в систему в структурированной форме, проходить автоматическую проверку и публиковаться как новая версия контента.

### 3.5. Отсутствующие данные не равны отрицательному ответу

Для клинического факта различаются как минимум состояния:

- «да»;
- «нет»;
- «неизвестно»;
- «не оценивалось / еще не запрашивалось».

Если для выбора клинической ветви необходим факт, которого нет, система не имеет права автоматически трактовать его как «нет». Она должна запросить значение либо завершить промежуточный расчет состоянием «необходимы дополнительные данные».

Для данных, необходимых только для коррекции дозировки, действует ранее согласованное правило: если данных для коррекции нет, используется базовый режим дозирования, заданный схемой, и этот факт отражается в трассировке.

## 4. Пользователи системы

### 4.1. Врач

Врач должен иметь возможность:

- начать новый расчет;
- выбрать нозологию;
- заполнить клинические признаки и доступные лабораторные показатели;
- указать сопутствующие лекарственные препараты;
- получить рекомендацию;
- увидеть объяснение решения;
- скопировать готовую текстовую рекомендацию в медицинскую документацию;
- оставить обратную связь о результате;
- просмотреть свои предыдущие обезличенные расчеты в пределах доступных прав.

### 4.2. Клинический фармаколог

Имеет функции врача и дополнительно должен иметь расширенный просмотр причин ограничения препаратов, взаимодействий, источников и технической трассировки решения.

### 4.3. Клинический администратор

На версии 0.1.0 не получает визуальный конструктор медицинских деревьев. Его задачи:

- просматривать версии медицинского контента;
- загружать подготовленный пакет правил;
- запускать валидацию;
- просматривать ошибки импорта;
- публиковать только валидированный пакет при наличии необходимых полномочий;
- активировать утвержденную версию для новых расчетов;
- выгружать данные для медицинской проверки.

Полноценный визуальный редактор правил относится к последующим версиям.

### 4.4. Системный администратор

Управляет пользователями, ролями, конфигурацией, техническим аудитом и эксплуатационными настройками. Системный администратор не должен иметь возможности незаметно изменять опубликованные медицинские правила.

## 5. Пользовательский сценарий врача

### 5.1. Начало работы

После авторизации врач открывает новый клинический случай. В версии 0.1.0 не должны вводиться ФИО, номер полиса, телефон, адрес и другие прямые идентификаторы пациента.

Допустимо хранение обезличенных клинических данных, необходимых для расчета и анализа работы системы.

### 5.2. Выбор нозологии

Врач выбирает одну из шести нозологий. После этого интерфейс показывает только те вопросы, которые могут потребоваться выбранному дереву или следующим этапам обработки.

### 5.3. Ввод клинических фактов

Интерфейс должен поддерживать:

- логические признаки;
- числовые значения;
- перечисления;
- лабораторные показатели с единицами измерения;
- группы факторов с начислением баллов;
- признаки анамнеза;
- данные о беременности/лактации и других ограничениях, когда они релевантны правилам.

Пользователь не должен видеть внутренние идентификаторы правил и узлов.

### 5.4. Сопутствующая терапия

Врач получает поле поиска препарата с автодополнением по справочнику. Выбранный препарат должен сохраняться как структурированный `drug_id`.

Если препарат не найден в справочнике, приложение может сохранить свободный текст как «нераспознанный препарат», но обязано явно сообщить, что для такого элемента автоматическая проверка лекарственных взаимодействий не гарантирована.

Для списка сопутствующей терапии должны различаться состояния:

- пациент не принимает постоянных препаратов;
- список препаратов введен;
- информация о сопутствующей терапии неизвестна.

При неизвестном списке система не должна писать, что взаимодействия «отсутствуют»; она должна сообщить, что проверка неполная.

### 5.5. Расчет

Клинический расчет выполняется на сервере. Интерфейс не содержит самостоятельной копии медицинских правил.

В процессе система может вернуть состояние «требуются данные» и перечислить конкретные факты, необходимые для продолжения.

### 5.6. Результат

Итоговый экран должен содержать:

- нозологию;
- итоговый тип результата;
- выбранную схему;
- первую линию терапии;
- альтернативы;
- дозу и режим, доступные в текущей версии;
- предупреждения;
- причины исключения препаратов, если это уместно для роли пользователя;
- статус проверки лекарственных взаимодействий;
- источники медицинских правил;
- версии всех использованных пакетов;
- краткое объяснение «почему система получила такой результат».

Результат должен иметь кнопку копирования структурированного текста.

## 6. Терминальные состояния

Версия 0.1.0 использует четыре технически различимых конечных состояния:

| Код | Смысл для врача |
|---|---|
| `ABT_NOT_INDICATED` | Антибактериальная терапия не показана по текущей клинической ветви. |
| `NO_APPLICABLE_DRUG` | Схема сформирована, но после фильтрации безопасности не осталось применимого препарата. |
| `NOT_COVERED_BY_GUIDELINE` | Комбинация условий не предусмотрена используемой клинической рекомендацией. |
| `ESCALATE_HOSPITALIZATION` | Требуется рассмотреть госпитализацию или иной уровень эскалации вместо стандартного амбулаторного назначения. |

Эти состояния нельзя заменять пустым списком препаратов или одним общим сообщением об ошибке.

## 7. Клинические модули

### 7.1. Клинический Rule Engine

Исполняет только нозологическое дерево и возвращает схему или терминальное состояние. Не должен самостоятельно проверять взаимодействия или рассчитывать дозу.

### 7.2. Scheme Resolver

Преобразует внутренний `scheme_id` в структурированный перечень лекарственных вариантов: первая линия и альтернативы.

### 7.3. Safety Engine

Получает кандидатов и применяет:

1. правила противопоказаний;
2. правила лекарственных взаимодействий.

Препарат не удаляется бесследно: его исходный статус и причина исключения должны сохраняться в трассировке.

### 7.4. Dose Engine

Получает допустимый препарат и его базовый режим. Если для него имеется валидированное правило коррекции и достаточно данных, формирует скорректированный режим. Если необходимые для коррекции данные отсутствуют, в версии 0.1.0 используется базовый режим согласно согласованной политике.

### 7.5. Recommendation Composer

Собирает итоговую рекомендацию из структурированных данных. Готовый медицинский текст не должен быть единственным источником информации в базе.

### 7.6. Decision Trace

Сохраняет последовательность обработки. По трассировке должно быть возможно восстановить, почему выбран конкретный исход.

## 8. Статус медицинского контента v0.1.0

| Компонент | Статус | Что реализует техническая команда | Что требуется от медицинской команды |
|---|---|---|---|
| Шесть клинических деревьев | Формализованы как ruleset 0.1.0 | Импорт, компиляция, исполнение, тестирование, трассировка | Проверить формализацию и подписать эталонные случаи |
| Справочник препаратов | Создан технический реестр с целыми ID | Поддержка ID, поиска, алиасов, связи со схемами | Проверить названия и состав списка |
| Противопоказания | Есть mock-контракт | Импорт, валидация, действия `BLOCK/WARN/ALLOW/REVIEW_REQUIRED` | Заполнить и валидировать реальные правила и источники |
| Лекарственные взаимодействия | Есть mock-контракт «светофор» | Импорт, сравнение с сопутствующей терапией, предупреждения, аудит | Заполнить пары, категории, действия, рекомендации и источники |
| Коррекция дозировки | Архитектура подготовлена, клиническое наполнение отложено | Реализовать модуль и fallback на базовый режим | Предоставить валидированные dose rules и правила расчета производных показателей |
| Источники правил | Частично указаны через исходную презентацию | Хранить provenance в каждой версии | Предоставить окончательные ссылки на клинические рекомендации/разделы |
| Golden cases | Еще не предоставлены | Поддержать автоматические regression tests | Подготовить эталонные клинические сценарии и ожидаемые результаты |

**Важно:** наличие технической поддержки противопоказаний, взаимодействий или дозовых правил не означает, что соответствующий медицинский справочник уже валидирован. Mock-данные должны быть выключены и не могут использоваться как клинические рекомендации.

## 9. Версионирование медицинского контента

Должны независимо версионироваться:

- клинический ruleset;
- справочник препаратов;
- правила противопоказаний;
- правила лекарственных взаимодействий;
- dose rules;
- формы/метаданные пользовательских вопросов при необходимости.

Каждый расчет сохраняет версии и контрольные хэши использованных пакетов.

Опубликованный пакет имеет жизненный цикл:

```text
DRAFT → IN_REVIEW → VALIDATED → PUBLISHED → RETIRED
```

Расчеты для врача выполняются только по опубликованной версии.

## 10. История расчетов и обратная связь

Для каждого завершенного расчета сохраняются:

- технический идентификатор;
- дата и время;
- пользователь;
- нозология;
- обезличенный snapshot входных данных;
- версии контента;
- исход клинического дерева;
- лекарственные кандидаты;
- результат safety-этапа;
- результат дозирования;
- итоговая рекомендация;
- Decision Trace.

Врач после получения результата должен иметь возможность отметить:

- согласен / не согласен;
- использовал рекомендацию / не использовал;
- комментарий свободным текстом.

Изменение заполненной формы после расчета не должно переписывать старый результат. Новый запуск создает новую оценку с новым immutable snapshot.

## 11. Выгрузка данных

### 11.1. Для врача

Обязательна возможность скопировать итоговый текст рекомендации.

### 11.2. Для медицинской команды

Авторизованный пользователь должен иметь возможность выгрузить обезличенные данные в XLSX или CSV для последующего анализа.

В выгрузку включаются входные признаки, результат, версии пакетов, технические терминальные состояния, факт применения рекомендаций и обратная связь.

Печатная форма и PDF допустимы как дополнительная функция, но в версии 0.1.0 не являются более приоритетными, чем XLSX/CSV и копирование результата.

## 12. Требования к интерфейсу

Интерфейс ориентирован на рабочее место врача и планшет.

Основной вариант:

- левое меню: новый расчет, история, доступные разделы;
- центральная рабочая область: пошаговые клинические вопросы;
- компактный контекстный блок результата/объяснения;
- крупные понятные состояния «Да / Нет / Неизвестно»;
- отображение единиц измерения рядом с числовым полем;
- минимальное число одновременно показываемых вопросов;
- возможность вернуться на предыдущий шаг;
- четкое предупреждение, если каких-либо данных недостаточно;
- финальная рекомендация визуально отделена от предупреждений и источников.

Это не свободный чат. Интерфейс представляет собой формальный диалоговый workflow.

## 13. Требования к технической реализации

Техническая команда должна реализовать:

1. веб-приложение на TypeScript/JavaScript-стеке;
2. отдельный серверный API;
3. чистое детерминированное ядро Rule Engine;
4. компилятор/importer authoring-данных в canonical RulePackage;
5. автоматический structural/semantic validator;
6. Scheme Resolver;
7. Safety Engine;
8. Dose Engine с архитектурой расширения;
9. Recommendation Composer;
10. Decision Trace;
11. PostgreSQL-хранилище истории и версий;
12. авторизацию и ролевой доступ;
13. аудит изменений медицинского контента;
14. историю обезличенных расчетов;
15. обратную связь врача;
16. XLSX/CSV-экспорт;
17. автоматические unit, integration, clinical regression и end-to-end тесты;
18. адаптивный интерфейс для десктопа и планшета.

## 14. Что требуется от медицинской команды

До завершения клинической приемки медицинская команда должна:

1. проверить машинное представление всех шести деревьев версии 0.1.0;
2. подтвердить ранее выполненные нормализации неоднозначностей презентации;
3. предоставить набор эталонных клинических случаев по каждой нозологии;
4. заполнить справочник противопоказаний в согласованном формате;
5. заполнить справочник лекарственных взаимодействий;
6. определить действие системы для каждой записи: блокировать, предупреждать, разрешать либо требовать ручной оценки;
7. предоставить источники для противопоказаний и взаимодействий;
8. проверить справочник препаратов и алиасы названий;
9. предоставить и валидировать dose rules, если коррекция дозы включается в клиническую эксплуатацию;
10. определить, какие предупреждения должен видеть обычный врач, а какие — только клинический фармаколог;
11. утвердить шаблон итоговой текстовой рекомендации;
12. принять результаты regression-тестов перед публикацией версии.

## 15. Что не входит в версию 0.1.0

- интеграция с ЕМИАС/МИС;
- OCR бумажных и PDF-анализов;
- автоматическое извлечение сведений из медицинской карты;
- полноценный визуальный конструктор медицинских правил;
- педиатрические режимы;
- стационарные алгоритмы;
- генеративный ИИ для выбора терапии;
- нативное мобильное приложение;
- электронная подпись заключения;
- автоматическое признание mock-справочников медицински валидированными.

Архитектура должна позволять добавлять эти возможности позднее без переписывания клинического ядра.

## 16. Критерии приемки версии 0.1.0

Версия считается технически готовой к медицинскому пилоту, если одновременно выполнено следующее:

- все шесть нозологий исполняются серверным Rule Engine;
- runtime не исполняет клинические строки через `eval`/`exec`;
- опубликованный ruleset проходит structural и semantic validation;
- отсутствуют циклы и битые ссылки в графе;
- состояние неизвестного обязательного факта приводит к запросу данных, а не к ложному `FALSE`;
- каждый завершенный расчет имеет воспроизводимый Decision Trace;
- результат содержит идентификаторы версий и хэши медицинского контента;
- схемы разрешаются в структурированные лекарственные варианты;
- safety-модули технически подключены, а невалидированные mock-правила выключены;
- в случае отсутствия данных для dose adjustment используется базовый режим согласно политике 0.1.0;
- результаты и обратная связь сохраняются без прямых идентификаторов пациента;
- медицинская команда может получить XLSX/CSV-выгрузку;
- врач может скопировать итоговую рекомендацию;
- интерфейс работает на актуальных десктопных браузерах и планшете;
- есть автоматические тесты и набор golden cases, утвержденный медицинской командой.

## 17. Предлагаемые этапы реализации

### Этап A. Каркас системы

Монорепозиторий, web, API, база данных, авторизация, роли, CI, базовая наблюдаемость.

### Этап B. Клинический Rule Engine

Compiler/importer, canonical RulePackage, validator, исполнение всех шести деревьев, Decision Trace.

### Этап C. Интерфейс клинического случая

Формы, пошаговая навигация, `UNKNOWN/NOT_ASSESSED`, запрос недостающих фактов, результат и объяснение.

### Этап D. Therapy/Safety/Dose

Scheme Resolver, реестр препаратов, импорт противопоказаний и DDI, Dose Engine с базовым режимом и будущими правилами коррекции.

### Этап E. История и исследовательский контур

Сохранение snapshot, feedback, аудит, XLSX/CSV-экспорт.

### Этап F. Медицинская валидация

Golden cases, исправление медицинского контента, публикация правил для пилота.

### Этап G. Пилот

Ограниченное использование, сбор обратной связи, оценка расхождений с экспертными решениями и подготовка следующей версии.

## 18. Главный принцип взаимодействия команд

Техническая команда отвечает за корректное, воспроизводимое и безопасное исполнение медицинских правил. Медицинская команда отвечает за клиническую корректность самих правил и справочников.

Система должна позволять обеим сторонам независимо проверить свою часть: разработчику — технический trace и валидность графа, медику — понятную последовательность клинического решения и источники.
